# Защищённый REST API на Python

Учебный API личных заметок: **Flask + SQLite + JWT**, с проверками безопасности в GitHub Actions. Весь backend находится в `app.py`. Пользователь входит по логину и паролю, создаёт заметки и читает только свои записи.

## Быстрый запуск

Нужен **Python 3.14**. Команды для macOS/Linux:

```bash
git clone https://github.com/trikesh32/infosec-1.git
cd infosec-1
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

# Случайный секрет подписи JWT для текущей сессии терминала.
export JWT_SECRET="$(python -c 'import secrets; print(secrets.token_hex(32))')"

# Пароль вводится интерактивно дважды, без отображения на экране.
flask --app app create-user alice
flask --app app run --host 127.0.0.1 --port 5000
```

Для Windows PowerShell: активация — `.venv\Scripts\Activate.ps1`, установка секрета — `$env:JWT_SECRET = python -c "import secrets; print(secrets.token_hex(32))"`.

Логин: 1–64 символа; пароль: 12–128. Пробелы по краям логина удаляются при создании. Готовых пользователей и паролей нет. Второго пользователя можно создать той же CLI-командой с другим логином.

База `instance/notes.sqlite` и таблицы создаются автоматически; данные сохраняются между перезапусками. Без `JWT_SECRET` длиной минимум 32 байта приложение не запускается. Длина не гарантирует случайность: используйте генератор выше.

При постоянном развёртывании сохраните секрет в защищённых переменных окружения. Генерация нового секрета делает старые токены недействительными. `.env` автоматически не загружается и исключён из Git вместе с базой и виртуальным окружением.

## API и примеры curl

| Метод | Путь | Назначение | Доступ |
| --- | --- | --- | --- |
| POST | `/auth/login` | Получить JWT | Без токена |
| GET | `/api/data` | Последние 100 своих заметок, новые первыми | Bearer JWT |
| POST | `/api/data` | Создать свою заметку | Bearer JWT |

POST-запросы принимают JSON. Защищённые методы требуют заголовок `Authorization: Bearer <токен>`.

### Вход

Во втором терминале выполните запрос, заменив `YOUR_PASSWORD` паролем, введённым при создании пользователя. Это обозначение, а не встроенный пароль. Не сохраняйте реальные пароли в истории команд на общей машине.

```bash
curl -i http://127.0.0.1:5000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"YOUR_PASSWORD"}'
```

Ответ `200 OK`:

```json
{"access_token":"<JWT>","token_type":"Bearer","expires_in":900}
```

Скопируйте значение `access_token`:

```bash
TOKEN='<JWT из ответа>'
```

### Создание заметки — третий метод по заданию

```bash
curl -i http://127.0.0.1:5000/api/data \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"text":"Моя первая заметка"}'
```

Ответ `201 Created`:

```json
{"id":1,"text":"Моя первая заметка"}
```

Поле `text` — строка длиной 1–1000 символов после удаления пробелов по краям. Владельца сервер берёт из проверенного JWT; переданный в JSON `user_id` игнорируется.

### Получение заметок

```bash
curl -i http://127.0.0.1:5000/api/data \
  -H "Authorization: Bearer $TOKEN"
```

Ответ `200 OK`:

```json
[{"id":1,"text":"Моя первая заметка"}]
```

Без заметок возвращается `[]`. Второй пользователь не увидит записи первого.

### Проверка отказа без токена

```bash
curl -i http://127.0.0.1:5000/api/data
```

Ответ `401 Unauthorized`:

```json
{"error":"Требуется Bearer-токен"}
```

### Ошибки

| Код | Причина |
| --- | --- |
| 400 | Некорректный JSON, тип или длина поля |
| 401 | Неверные учётные данные, отсутствующий, испорченный или просроченный JWT |
| 413 | Тело запроса больше 16 КиБ |
| 415 | Тело передано без JSON Content-Type |
| 429 | Превышен лимит запросов |

Ожидаемые HTTP-ошибки возвращаются в JSON с полем `error`.

## Реализованная защита

### SQL-инъекции

Все SQL-запросы с пользовательскими значениями используют параметры SQLite `?`. Данные передаются отдельно от текста запроса:

```python
db().execute("SELECT id, password_hash FROM users WHERE username = ?", (username,))
```

Логин `' OR 1=1 --` воспринимается как строка и не меняет условие SQL. Аналогично обрабатывается текст заметок. `executescript()` используется только для постоянной схемы таблиц без пользовательских данных.

### XSS

Текст хранится в исходном виде и экранируется **при выдаче** через `markupsafe.escape()`, чтобы избежать повторного экранирования. Например, `<script>alert(1)</script>` в JSON-значении становится `&lt;script&gt;alert(1)&lt;/script&gt;`.

Ответы имеют `Content-Type: application/json`, `X-Content-Type-Options: nosniff` и ограничивающий CSP. Сам JSON не исполняет HTML. Экранирование выполняет требование задания для HTML-контекста; оно не является универсальной защитой для JavaScript, URL или CSS. Будущий frontend должен выводить текст через `textContent`, не вставлять недоверенные строки через `innerHTML`.

### Пароли, JWT и контроль доступа

- Пароли хэшируются `generate_password_hash(method="scrypt")` из Werkzeug со случайной солью. В SQLite хранится только хэш с параметрами алгоритма и солью. Проверка — через `check_password_hash()`.
- После входа выдаётся JWT с подписью **HS256**, действующий **15 минут**. Ключ берётся из окружения, в коде его нет.
- Декоратор `jwt_required` проверяет подпись, фиксированный алгоритм, срок действия, издателя, аудиторию и наличие обязательных полей `sub`, `iat`, `exp`, `iss`, `aud`. Пользователь из `sub` должен существовать в базе.
- `sub` — строковый ID пользователя, `iat` — время выдачи, `exp` — срок действия, `iss` — издатель, `aud` — аудитория. Пароля и заметок в токене нет.
- JWT подписан, **но не зашифрован**: payload читается без ключа. Токен нельзя публиковать или передавать в URL.
- Чтение заметок всегда содержит `WHERE user_id = ?`. Создание также использует ID из проверенного токена.
- Неизвестный логин и неверный пароль дают одинаковую ошибку. Для неизвестного логина проверяется фиктивный scrypt-хэш, чтобы уменьшить различие времени ответа.
- Вход ограничен пятью запросами в минуту с IP. Для остальных маршрутов действует лимит 200 запросов в час с IP на маршрут.
- `Cache-Control: no-store` запрещает кэширование ответов. Аутентификация использует явный Bearer-заголовок, cookies для неё не используются.

## Тесты и локальные проверки

```bash
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
bandit -r app.py
pip-audit -r requirements.txt
```

Тесты используют временную SQLite-базу и случайные секреты; рабочая база не затрагивается. Проверяются вход, хэширование, отказ без токена, неверная подпись/алгоритм/аудитория JWT, истёкший и неполный токен, изоляция заметок, SQLi, XSS, валидация, размер запроса, ограничение входа и заголовки безопасности.

`pip-audit` требует доступ к сети. Зафиксированы прямые и транзитивные зависимости. После обновлений повторяйте тесты и SCA. Отсутствие предупреждений сканера не доказывает отсутствие всех уязвимостей.

## GitHub Actions: SAST и SCA

Конфигурация: [`.github/workflows/ci.yml`](.github/workflows/ci.yml). На каждом **push** и **pull request**, а также вручную через **Run workflow**, выполняются:

1. Установка зависимостей и `pytest`.
2. **SAST — Bandit:** анализ `app.py` на опасные конструкции. Любая найденная проблема делает шаг неуспешным.
3. **SCA — pip-audit:** проверка runtime-зависимостей, включая транзитивные, на известные уязвимости. Любая найденная уязвимость делает шаг неуспешным.
4. Загрузка JSON-результатов в артефакт `security-results`, доступный 14 дней. Сканеры запускаются и при падении тестов; загрузка результатов выполняется и при ошибке сканера.

Это учебный CI с security-проверками; автоматическое развёртывание не настроено.

### Snyk по условию задания

Дополнительно настроен SCA через **Snyk**. Для включения:

1. Получите API token в своём аккаунте Snyk.
2. Откройте репозиторий → **Settings → Secrets and variables → Actions → New repository secret**.
3. Создайте секрет **`SNYK_TOKEN`**, вставьте токен как значение.
4. Выполните push либо запустите workflow вручную.

Snyk проверяет `requirements.txt`, сохраняет `snyk-report.json` в артефакт `snyk-results` и завершает шаг с ошибкой при **High/Critical**. Без токена выводится предупреждение о пропуске Snyk; это не означает успешное сканирование Snyk. Основной SCA через pip-audit работает без секретов на каждом push и PR.

Snyk запускается на push и ручном запуске. На PR он отключён, чтобы не передавать секрет в окружение кода pull request. Для буквального выполнения требования об использовании Snyk или OWASP Dependency-Check включите Snyk и получите успешный запуск после push.

В [Actions репозитория](https://github.com/trikesh32/infosec-1/actions/workflows/ci.yml) выберите запуск и проверьте **Tests**, **SAST — Bandit**, **SCA — pip-audit** и при включённом Snyk — **SCA — Snyk**. JSON-файлы доступны в разделе **Artifacts**. Ссылка на отдельный запуск имеет вид `https://github.com/trikesh32/infosec-1/actions/runs/<run_id>`.

Отдельный отчёт и скриншоты не включены. Реальный запуск GitHub Actions появится после отправки кода в репозиторий; локальные тесты не заменяют его.

## Ограничения учебного примера

Для локальной демонстрации используется Flask development server на `127.0.0.1`, без debug-режима. При размещении в интернете нужны HTTPS, production WSGI-сервер и защищённое хранение секрета и базы.

Счётчики Flask-Limiter находятся в памяти: обнуляются при перезапуске и не разделяются между процессами. Для нескольких процессов потребуется общее хранилище, например Redis. За reverse proxy адрес клиента нужно настраивать только с учётом доверенных прокси.

Нет регистрации через API, refresh-токенов, индивидуального отзыва JWT, восстановления пароля и пагинации. JWT работает до истечения 15 минут; смена общего секрета отзывает все токены. GET возвращает только последние 100 записей. Эти ограничения оставлены, чтобы код был небольшим.

## Ответы на контрольные вопросы

**1. Почему bcrypt/scrypt/Argon2 предпочтительнее SHA-256 для паролей?**

SHA-256 рассчитан на быстрое вычисление, поэтому позволяет быстро перебирать пароли. Специализированные алгоритмы имеют настраиваемую стоимость и используют соль; scrypt и Argon2 также требуют значительного объёма памяти. Это повышает стоимость перебора после утечки базы.

**2. Чем отличаются SAST и DAST?**

SAST исследует исходный код без запуска приложения и ищет опасные конструкции. DAST проверяет работающий сервис запросами извне. Bandit — SAST. Проверки зависимостей относятся к SCA, а не к DAST.

**3. Как работает JWT?**

Токен состоит из header, payload и подписи. Header описывает алгоритм, payload содержит claims, например ID пользователя и срок действия. Сервер проверяет подпись ключом, заранее разрешённый алгоритм и ограничения claims. Изменение payload нарушает подпись; Base64-декодинг не подтверждает подлинность токена.

**4. Чем опасно отсутствие аудита зависимостей?**

Приложение может унаследовать известные уязвимости прямых и транзитивных библиотек: обход аутентификации, утечку данных, выполнение кода или отказ в обслуживании. SCA помогает обнаружить опубликованные проблемы, но не заменяет обновления, тестирование и анализ своего кода.
